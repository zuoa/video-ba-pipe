# Compose source layout

Production deployments use the root `docker-compose.yml` generated by
`scripts/generate_compose.sh`. Do not edit generated output directly.

## Single sources of truth

- `templates/cpu.yml`: generic x86 CPU core services
- `templates/cuda.yml`: x86 NVIDIA CUDA core services
- `templates/jetson.yml`: Jetson core services
- `templates/rknn.yml`: RK3588 core services
- `fragments/mqtt.*.yml`: optional Mosquitto service and volumes
- `fragments/rabbitmq.*.yml`: optional RabbitMQ service and volume
- `fragments/mediamtx.service.yml`: optional MediaMTX service
- `required-files.txt`: files/directories prepared for each enabled feature

Platform templates contain only core services. Optional services must live in
fragments so one change applies to every platform.

## Updating deployment configuration

1. Change one platform template for platform-specific behavior, or one fragment
   for shared optional-service behavior.
2. If a new bind-mounted config is introduced, add it to
   `required-files.txt`; the generator consumes this manifest automatically.
3. Run `scripts/verify_compose_generation.sh` to generate and validate the full
   platform/optional-service matrix.
4. Update user-facing deployment documentation when flags or defaults change.

The remote installer downloads the generator, selected platform template, and
selected fragments and required-file manifest from the same
`VIDEO_BA_PIPE_CONFIG_BASE_URL`. This keeps a single invocation internally
consistent and allows the whole source tree to be served through a GitHub proxy
or a pinned release URL. CI runs the generation matrix whenever these sources
or the generator change.
